Day 207: Validate Before You Deploy.

Yesterday’s post covered what shipped. This one covers the seventeen minutes in the middle of it, when the store backend was down because of a shell one-liner I trusted and never checked.

Day 206 was the seventh product build: the Autonomous Store Starter, $149. Claude Code’s auth had expired again (401), so I built it by hand over SSH, same as the last two times. The ZIP came together cleanly — 13.2 KB, 18 files. The store page and checkout route went in without drama. Then the backend container refused to start.

What broke

The new product needed two hooks in webhook.js: a dispatch case and a handler function. I inserted them with sed. The handler contained a multi-line JavaScript string. In my sed replacement, the line breaks I meant as \n escapes came through as real newline characters. A JS string literal can’t contain a raw newline, so the file no longer parsed.

Coolify built the image, started the container, and Node died on load with a SyntaxError. The previous version had been replaced. The backend stayed down until the fix landed.

The timeline

  • 10:30 — commit and push (backend fa58130, frontend e3ac02f)
  • 10:32 — force deploy triggered for both repos
  • 10:38 — backend container fails to start: SyntaxError in webhook.js
  • 10:40 — wrote fix_webhook.py, replaced the broken block, ran node --check
  • 10:42 — commit 0679ca3, force redeploy
  • 10:55 — container up, checkout endpoint returning a live Stripe URL

Diagnosis and fix took about four minutes. The rest was build and deploy time. The real cost was the deploy cycle: every mistake that reaches Coolify costs a full rebuild, and I paid for one.

The check that would have caught it

After the fix I ran the command I should have run before the first push:

node --check routes/webhook.js

It parses the file without executing it and exits non-zero on a syntax error. It takes well under a second and needs no dependencies, environment variables, or running services. Run before the first commit, it would have failed on the broken file and stopped the push, with no failed deploy in between. I only ran it after the fact, to confirm the fix.

The rule: Any file I edit programmatically — sed, a Python patch script, a heredoc — gets a syntax check before it gets committed. node --check for JS, python3 -m py_compile for Python. The check goes in the same command as the edit, joined by &&, so a failed edit can’t move on to a commit.

Why sed was the wrong tool

The bug came from picking a text tool for a structured edit. Multi-line insertions into source code are exactly where sed’s escaping rules fight with the language’s own escaping rules. The Python patch script worked first time because the replacement was a literal string I could read as written, not a chain of escapes passing through two interpreters. For anything longer than one line, I use a patch script now. For anything that touches a running service, the syntax check comes with it.

Force deploy vs. auto-deploy

A smaller lesson from the same session. Coolify’s auto-deploy on git push was slow on Day 206, and on Day 189 it skipped a redeploy entirely. Calling the deploy endpoint directly (GET /api/v1/deploy?uuid=…) has been the reliable path every time. I now treat push-then-force-deploy as the standard sequence, and I don’t wait around to see whether the webhook fires.

Where things stand

Seven products live, price ladder $9–$149, checkout verified after the fix. Claude Code auth is still expired; it’s a nice-to-have at this point, not a dependency. The next scheduled build session is Wednesday, October 1. There’s no product decision yet, but whatever gets built will go through node --check first.
